# Integration path

The payment-capable regtest node uses PQLN's LDK fork through a patched LDK Node and a direct Bitcoin P2P chain source. The independent `ChainWatch` remains a separate read-only tool. The node's peer adapter matches compact filters against wallet addresses and LDK channel scripts. It downloads full blocks only on a filter match and otherwise advances the wallet, channel manager, channel monitors, and sweeper with a block header. LDK's chain poller disconnects old blocks and connects the winning branch after a reorganization.

## Intended boundary

1. The pinned PQLN fork is the Lightning protocol engine. The LDK Node patch uses the hybrid PQ transport for inbound and outbound TCP connections, and requires PQ inbound and outbound payment onions. The CLI checks invoices against an independently trusted ML-DSA key before requesting payment. It does not use a classical fallback.
2. LDK Node provides the on-chain wallet, funding and sweep machinery, channel monitor persistence, and fixed regtest fee estimates. Kyoto fetches headers and blocks from a selected Bitcoin P2P peer and relays transactions to it. No Esplora, Electrum, or Bitcoin Core RPC endpoint is configured in the Lightning client. Bitcoin Core is only a test fixture for mining blocks.
3. The peer adapter scans verified compact filters from genesis on regtest. The watch set includes both keychains' revealed wallet scripts and scripts registered by LDK for funding transactions and monitored outputs. It keeps those scripts for the process lifetime; persisted wallet addresses and channel monitor registrations are reconstructed on restart. The wallet advances its BDK chain state on a header-only block. A matching filter causes a full block download, including all transactions needed if LDK registers another output while processing that block.
4. The automated regtest filter check downloaded zero full blocks across 101 unrelated blocks, then one full block when its watched wallet address was funded. A second automated check funds two PQLN clients, opens and confirms an announced channel, pays a PQ invoice, restarts both clients, pays again, disconnects a mined block in a one-block reorganization, and pays a third invoice on the replacement branch. On a peer failure during that reorganization, the Bitcoin peer session restarts and replays its filters before chain polling resumes.

This remains a regtest research implementation. A single configured Bitcoin peer can omit a matching filter and hide a payment or spend; filter-header validation against that same peer does not prevent this. A production channel wallet needs independent peer comparison or another way to detect omissions, plus continuous operation or a watchtower. The prototype also lacks mempool observation and uses fixed regtest fee estimates. The independent `ChainWatch` JSON journal is **not** LDK's channel persistence.
5. Review upstream protocol identifiers, key pinning, interoperability, size limits, offline monitoring, and the research fork's production-hardening gap before considering any mainnet use.

LDK documents [BIP157/158 as a valid block source](https://lightningdevkit.org/blockchain_data/). The current adapter takes the conservative full-block path while the registered script and outpoint watch set is unfinished.

## Security boundary

PQLN protects Lightning's **off-chain** communication when both sides use its mechanisms and the payee/node keys have a trustworthy anchor. It does not make Bitcoin channel outputs post-quantum safe. The PQLN authors' own [threat model](https://github.com/ahmet-kurt/pq-rust-lightning#threat-model) leaves channel-fund theft through on-chain keys outside its scope. Key pinning on first sight is also vulnerable if the first contact occurs after a quantum-capable attacker exists ([authors' discussion](https://delvingbitcoin.org/t/pqln-post-quantum-security-for-the-bitcoin-lightning-networks-off-chain-surfaces/2893)).

An offline phone cannot react to a revoked commitment or a time-sensitive sweep by itself. A payment-capable mobile design therefore needs an explicit monitoring and recovery plan before holding real funds. This repository can create regtest keys and channels, but does not provide that offline monitoring plan.
